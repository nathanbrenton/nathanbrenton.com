The same revision cycle now also records the Weekly Operations Digest as

The 2026-08-25 Alloy + Loki revision additionally records local log aggregation

Grafana is deliberately on-demand because continuous Grafana + Loki + Alloy
operation creates avoidable memory pressure on this approximately 1-GiB VPS.

Commissioning also established a resource-constrained deployment method:
large package inspection must use disk-backed /var/tmp rather than this host's
small tmpfs-backed /tmp; occupied swap is not itself a failure signal; sustained
swap I/O and Linux PSI are the more important pressure indicators; and service
installation/configuration must be staged and measured before enabling the
next component.

The older public-server rebuild workflow remains useful as historical source
material, but the intent of this revision is for this document to become the
single authoritative machine-rebuild runbook.

This runbook now covers TWO deliberately independent mail roles:

1. Operational/status mail generated by this server and sent outward.
2. Public business/contact mail received for nathanbrenton.com and hiplingo.com,
   then forwarded to a separate contact destination.

It also records the nginx hidden-path hardening added after public scanners
requested paths such as /.git/config and /.env.

The August 18, 2026 update additionally records the Hiplingo public-media
filesystem boundary needed by metadata-editor's atomic media deployment.
That permission model matters operationally because nginx must remain
read-only while the dedicated media deploy identity must be able to create
temporary sibling directories during an atomic publication swap.

This document intentionally emphasizes final architecture, why each mail
technology is present, validated behaviors, safe rebuild/maintenance checks,
and operational boundaries. Troubleshooting detours are omitted except where
they explain an important security property.


2026-09-08 CURRENT MONITORING OVERRIDES / REBUILD INVARIANTS
------------------------------------------------------------
The monitoring stack continued to mature after the 2026-08-25 commissioning
sections below were written. For a NEW server build, these current invariants
supersede older commissioning-era wording where the two conflict:

    - Grafana is an ON-DEMAND investigation UI. It is installed and
      loopback-only, but intentionally inactive + disabled at boot on the
      current approximately 1-GiB host. Monit must NOT treat an intentionally
      stopped Grafana service as a failure.

    - Loki + Alloy are always-on and are included in the local watchdog /
      Prometheus target model.

    - Independent Better Stack external monitoring is COMPLETE and should be
      treated as part of the first-build monitoring architecture, not as a
      future optional milestone.

    - The public external checks are content-aware HTTPS monitors rather than
      status-code-only checks. They verify expected site identity text as well
      as public reachability/TLS.

    - The daily report distinguishes core always-on services from on-demand
      Grafana, includes trailing-24-hour alert activity, Linux OOM/PSI context,
      observability/cache footprint, and real Fail2ban Ban/Unban history.

    - The weekly report includes a dedicated seven-day memory-pressure section:
          Kernel OOM kills
          PSI memory "some" p95
          PSI memory "full" p95

    - The weekly PSI values depend on node_exporter exposing:
          node_pressure_memory_waiting_seconds_total
          node_pressure_memory_stalled_seconds_total

      A rebuild must validate these two series before weekly-report
      commissioning. Do not silently omit or fabricate the metric if the
      destination kernel/node_exporter does not expose it.

    - Host-shape numbers in this runbook (1 vCPU, ~1 GiB RAM, ~3 GiB swap,
      30-GB root, and the resulting resource limits/thresholds) are
      web-prod-01-specific. Reuse the architecture for another server, but
      re-baseline RAM/CPU/swap/disk thresholds and cgroup limits against that
      server's actual capacity and workload.

The 2026-09-08 weekly memory-pressure implementation is informational in the
digest. Existing Prometheus/Alertmanager production rules remain the source of
incident thresholds; no extra public port, daemon, or alert rule is required
solely to render the weekly PSI/OOM section.



REBUILD ORDER — USE THIS SEQUENCE ON THE NEXT SERVER BUILD

This document is both a current-state record and a rebuild guide.

can be validated before the next layer depends on it:

    2. Remove UFW if present; nftables is the only host firewall.
    3. Create n8 plus the three dedicated deployment identities/groups.
    4. Install/reuse SSH public keys; prove n8 login before disabling root SSH.
    5. Apply final SSH hardening and prove a fresh hardened login.
    6. Apply bootstrap nftables policy: TCP 22/80/443 only.
    7. Configure unattended upgrades with automatic reboot disabled.
    8. Configure Fail2ban sshd jail using journald + nftables.
    9. Create web/deployment filesystem boundaries and bootstrap releases.
   10. Configure nginx + public web roots + hidden-path hardening.
   11. Configure web DNS and obtain site TLS certificates.
   12. Build Postfix + OpenDKIM + PostSRSd; validate locally before SMTP
       exposure; add public TCP/25 only after recipient/relay/SRS/TLS checks.
   13. Install server-health-report systemd service/timer.
   14. Install Monit local watchdog and native-SMTP alert delivery.
   15. Install node_exporter on loopback TCP/9100; verify host/systemd
       telemetry AND node_pressure_memory_waiting_seconds_total /
       node_pressure_memory_stalled_seconds_total before reporting depends on
       them.
   16. Install Prometheus on loopback TCP/9090.
   17. Install Grafana OSS on loopback TCP/3000 with Prometheus datasource.
   18. Install Blackbox Exporter on loopback TCP/9115.
   19. Add Prometheus blackbox_https probes for both public websites.
   20. Rebuild the 34-panel "web-prod-01 - Operations" Grafana dashboard.
   21. Install Alertmanager on loopback TCP/9093 with HA gossip disabled.
   22. Connect Prometheus to Alertmanager and load production rule files.
   23. Add independent Monit watchdogs for node_exporter, Prometheus,
       Alertmanager and Blackbox Exporter. Do not make Grafana an always-on
       Monit dependency; its intended steady-state may be inactive.
   24. Run synthetic FIRING + RESOLVED tests, then remove test scaffolding.
   25. Run the complete Alerting v1 final audit.
   26. Install and validate Prometheus-backed Daily Server Health Report v2.
   27. Run one controlled systemd/mail delivery test and verify:
       service Result=success, status=sent, queue empty, timer enabled/active.
   28. Install and validate the Weekly Operations Digest service/timer,

   29. Capacity-audit the host before adding log aggregation; inspect /tmp,

   38. Run the external-monitoring + heartbeat audit and retain the complete

Do not expose Grafana, Prometheus, Alertmanager, node_exporter, or Blackbox

FRESH VPS FOUNDATION — RECONCILED FROM THE 2026-08-19 WORKFLOW
---------------------------------------------------------------
The earlier web-prod-01 public-server rebuild workflow contained several
from-a-blank-VPS steps that were not reproduced at the same depth in the
initial observability runbook. Preserve these requirements in every rebuild.

A. Local rebuild variables / SSH keys
-------------------------------------
Use dedicated local keys. Reuse existing keys when rebuilding an existing
server rather than silently generating replacements.

    export SERVER_IP='<PUBLIC_IPV4>'
    export SERVER_HOST='web-prod-01'

    export ADMIN_KEY="$HOME/.ssh/web-prod-01-n8"
    export DEPLOY_NATHAN_KEY="$HOME/.ssh/web-prod-01-deploy-nathan"
    export DEPLOY_HIPLINGO_APP_KEY="$HOME/.ssh/web-prod-01-deploy-hiplingo-app"
    export DEPLOY_HIPLINGO_MEDIA_KEY="$HOME/.ssh/web-prod-01-deploy-hiplingo-media"

Generate only missing keys:

    test -f "$ADMIN_KEY" ||       ssh-keygen -t ed25519 -f "$ADMIN_KEY" -C 'n8@web-prod-01'

    test -f "$DEPLOY_NATHAN_KEY" ||       ssh-keygen -t ed25519 -f "$DEPLOY_NATHAN_KEY"         -C 'deploy-nathan@web-prod-01'

    test -f "$DEPLOY_HIPLINGO_APP_KEY" ||       ssh-keygen -t ed25519 -f "$DEPLOY_HIPLINGO_APP_KEY"         -C 'deploy-hiplingo-app@web-prod-01'

    test -f "$DEPLOY_HIPLINGO_MEDIA_KEY" ||       ssh-keygen -t ed25519 -f "$DEPLOY_HIPLINGO_MEDIA_KEY"         -C 'deploy-hiplingo-media@web-prod-01'

DO NOT paste private-key contents.

B. Initial provider/root session
--------------------------------
Use the provider's initial console/injected credential:

    ssh root@"$SERVER_IP"

Keep that root session open until n8 key authentication, sudo, SSH hardening,
and a fresh hardened n8 login have all been proven in a second terminal.

C. Patch OS / base packages
---------------------------

    apt update
    apt full-upgrade -y

    apt install -y       sudo       openssh-server       nftables       nginx       certbot       python3-certbot-nginx       fail2ban       unattended-upgrades       rsync       curl       ca-certificates       dnsutils       openssl

    hostnamectl set-hostname web-prod-01

D. Remove UFW before configuring nftables
-----------------------------------------
Do not run UFW and the direct nftables policy together.

    if dpkg-query -W ufw >/dev/null 2>&1; then
        systemctl disable --now ufw 2>/dev/null || true
        apt purge -y ufw
    fi

    dpkg-query -W ufw 2>/dev/null || echo 'ufw_package=absent'

Do not purge generic iptables compatibility packages merely because they
exist. nftables is the authoritative host firewall.

E. Create admin + deployment identities
----------------------------------------

    id n8 >/dev/null 2>&1 || adduser --disabled-password --gecos '' n8
    usermod -aG sudo n8

Set n8's local sudo/PAM password interactively with:

    passwd n8

Create groups:

    getent group nathan-deploy >/dev/null || groupadd nathan-deploy
    getent group hiplingo-app-deploy >/dev/null || groupadd hiplingo-app-deploy
    getent group hiplingo-media-deploy >/dev/null || groupadd hiplingo-media-deploy

Create deployment users:

    id deploy-nathan >/dev/null 2>&1 ||       useradd -m -s /bin/bash -g nathan-deploy deploy-nathan

    id deploy-hiplingo-app >/dev/null 2>&1 ||       useradd -m -s /bin/bash -g hiplingo-app-deploy deploy-hiplingo-app

    id deploy-hiplingo-media >/dev/null 2>&1 ||       useradd -m -s /bin/bash -g hiplingo-media-deploy deploy-hiplingo-media

Lock deployment-user passwords:

    passwd -l deploy-nathan
    passwd -l deploy-hiplingo-app
    passwd -l deploy-hiplingo-media

Create SSH directories:

    install -d -m 700 -o n8 -g n8 /home/n8/.ssh
    install -d -m 700 -o deploy-nathan -g nathan-deploy       /home/deploy-nathan/.ssh
    install -d -m 700 -o deploy-hiplingo-app -g hiplingo-app-deploy       /home/deploy-hiplingo-app/.ssh
    install -d -m 700 -o deploy-hiplingo-media -g hiplingo-media-deploy       /home/deploy-hiplingo-media/.ssh

Deployment authorized_keys entries use OpenSSH "restrict". This disables
forwarding, PTY allocation, X11 forwarding, agent forwarding and ~/.ssh/rc
while retaining deployment transport.

F. SSH hardening / backup-location rule
---------------------------------------
Do not fight cloud-init by editing its packaged include. Use:

    /etc/ssh/sshd_config.d/00-local-hardening.conf

CRITICAL BACKUP RULE:
    Never store backup copies inside a wildcard-consumed configuration
    directory. The SSH include pattern on this host can parse files such as
    *.conf.backup. The same principle applies to Monit conf.d and similar
    daemon include directories.

Use a non-included backup location:

    sudo install -d -m 700 /root/ssh-config-backups

Production SSH policy:

    PermitRootLogin no
    PasswordAuthentication no
    KbdInteractiveAuthentication no
    PubkeyAuthentication yes
    MaxAuthTries 3
    X11Forwarding no
    AllowUsers n8 deploy-nathan deploy-hiplingo-app deploy-hiplingo-media

Validate before reload:

    sudo sshd -t

    sudo sshd -T | grep -E       '^(maxauthtries|permitrootlogin|pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|x11forwarding|allowusers) '

Then:

    sudo systemctl reload ssh

Prove a NEW n8 login from another terminal before abandoning provider/root
access.

G. Bootstrap nftables policy
----------------------------
The initial firewall accepts only established/related traffic, loopback,
ICMP/ICMPv6 and new TCP 22/80/443. Input and forward default to DROP; output
defaults to ACCEPT.

Core bootstrap rule:

    tcp dport { 22, 80, 443 } ct state new accept

Validate before applying:

    sudo nft -c -f /etc/nftables.conf

Then:

    sudo systemctl enable nftables
    sudo systemctl restart nftables

Do NOT add public TCP/25 yet. SMTP is added only after the complete local
mail-recipient, anti-relay, SRS, DNS and TLS validation sequence.

H. Unattended upgrades
----------------------

    sudo tee /etc/apt/apt.conf.d/20auto-upgrades >/dev/null <<'EOF_APT'
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
EOF_APT

    sudo tee /etc/apt/apt.conf.d/52unattended-upgrades-local >/dev/null <<'EOF_REBOOT'
// Local production-server policy.
// Package updates may install automatically.
// Reboots remain an explicit administrator action.
Unattended-Upgrade::Automatic-Reboot "false";
EOF_REBOOT

    sudo systemctl enable --now apt-daily.timer apt-daily-upgrade.timer

I. Fail2ban
-----------
Use journald; do not install rsyslog merely to create /var/log/auth.log.

    /etc/fail2ban/jail.d/sshd.local

Production policy:

    [sshd]
    enabled = true
    backend = systemd
    banaction = nftables
    port = ssh
    maxretry = 5
    findtime = 10m
    bantime = 1h
    usedns = no

Validate:

    sudo fail2ban-client -t
    sudo systemctl enable fail2ban
    sudo systemctl restart fail2ban
    sudo fail2ban-client ping
    sudo fail2ban-client status sshd

A TEST-NET address such as 192.0.2.123 may be temporarily banned/unbanned to
prove nftables enforcement. Never use the administrator's actual client IP.

J. Deployment-boundary validation
---------------------------------
The deployment identities must be able to write only their own trees.

Required boundaries:

    deploy-nathan
        /var/www/nathanbrenton.com/releases/

    deploy-hiplingo-app
        /var/www/hiplingo.com/app/releases/

    deploy-hiplingo-media
        /var/www/hiplingo.com/published-media/
        AND sibling staging beneath /var/www/hiplingo.com/

Explicitly test both allowed writes and forbidden cross-boundary writes.

For Hiplingo media, also test the atomic sibling operation:

    probe="/var/www/hiplingo.com/published-media.metadata-editor-permission-probe.$$"
    mkdir "$probe" && rmdir "$probe"

This is distinct from merely proving write permission inside published-media.

DESIGN DECISIONS
----------------
1. Postfix is now a DUAL-ROLE MTA:
       - outbound operational mail; and
       - narrowly scoped inbound SMTP for public contact forwarding.

2. Postfix is NOT a general mailbox server:
       - no IMAP
       - no POP3
       - no user mailboxes
       - no submission service on TCP/587
       - no implicit TLS submission on TCP/465

3. Public SMTP listens only on:
       127.0.0.1:25
       45.32.88.137:25
   IPv6 SMTP is intentionally not enabled.

4. nftables is default-drop and explicitly permits inbound TCP/25 only after
   recipient validation, TLS, anti-relay behavior, SRS, DNS, and external
   client testing were completed.

5. Public recipient scope is intentionally explicit:
       operations/admin:
           admin@hiplingo.com

       business/public:
           info@nathanbrenton.com
           postmaster@nathanbrenton.com
           nathan@nathanbrenton.com
           info@hiplingo.com
           postmaster@hiplingo.com
           nathan@hiplingo.com
           licensing@hiplingo.com
           press@hiplingo.com
           accounting@hiplingo.com

       plus valid signed SRS bounce addresses only

   Unknown addresses receive SMTP 550 rejection instead of becoming a
   catch-all.

6. Unauthenticated arbitrary relay is forbidden. External relay testing
   returned SMTP 454. Localhost may relay because loopback is intentionally
   present in Postfix mynetworks for trusted local system submission.

7. Public contact forwarding uses SRS (Sender Rewriting Scheme). Forwarding
   commonly breaks the original sender's SPF because the final recipient sees
   the forwarding VPS as the connecting SMTP host. SRS replaces the envelope
   sender with a signed address under srs.nathanbrenton.com so SPF evaluates
   against the forwarding server and bounces can be safely reversed.

8. SRS does NOT make SPF align with the original visible From: domain for
   DMARC. Preserving the original sender's DKIM signature is therefore
   important; DKIM alignment can carry DMARC through forwarding even when the
   original SPF path would no longer align.

9. PostSRSd lookup ports 10001 and 10002 are loopback-only:
       10001 = forward sender rewrite
       10002 = reverse SRS validation/decoding

10. Public SMTP uses a dedicated Let's Encrypt certificate for:
        web-prod-01.nathanbrenton.com
    Postfix advertises opportunistic STARTTLS with smtpd_tls_security_level=may.
    The certificate renewal deploy hook reloads Postfix after renewal.

11. Operational sender identity remains separate:
        alerts@ops.nathanbrenton.com
    with independent SPF + DKIM + DMARC.

12. ADMIN_FORWARD_TARGET and CONTACT_FORWARD_TARGET are deliberately
    independent configuration responsibilities. They may currently resolve to
    the same real inbox, but changing one destination later must not change the
    other. ADMIN_EMAIL is the stable internal alias admin@hiplingo.com, not the
    real admin inbox.

13. No Gmail SMTP relay, Gmail App Password, or hosted mailbox provider is
    required for forwarding. The server speaks SMTP directly to recipient MX
    systems.

14. Monit CLI uses a root-only Unix control socket; TCP/2812 is not exposed.

15. Monit sends alerts with its built-in SMTP client directly to
    127.0.0.1:25. Production does NOT require a server-monitor-alert EXEC
    helper and does NOT require a /var/spool/postfix/maildrop sandbox
    exception.

16. The operational/admin destination has one canonical routing point:
        /etc/server-monitor/config      -> ADMIN_EMAIL=admin@hiplingo.com
        /etc/monit/conf.d/mail-alerts   -> set alert admin@hiplingo.com
        /etc/postfix/admin-forwarding.regexp -> ADMIN_FORWARD_TARGET

    Only the admin forwarding map changes when the real operations inbox moves.
    This remains independent from CONTACT_FORWARD_TARGET.

17. The public web roots are protected against hidden-file probes. A prior
    scanner request for /.git/config returned HTTP 200 only because the SPA
    fallback served index.html. Hash comparison proved the response was the
    normal app shell, and filesystem scans found no .git/config or .env files.
    nginx now returns 404 for hidden paths such as /.git/* and /.env.


18. Hiplingo public media uses a dedicated deployment identity and a deliberately
    asymmetric filesystem boundary:

        /var/www/hiplingo.com
            root:hiplingo-media-deploy
            mode 3775  (SGID + group-write + sticky bit)

        /var/www/hiplingo.com/app
            root:hiplingo-app-deploy
            mode 2775

        /var/www/hiplingo.com/published-media
            owned by deploy-hiplingo-media after the first atomic deployment
            normal live mode 0755

    metadata-editor stages an upload as a sibling path such as:

        published-media.metadata-editor-incoming.<operation-id>

    The media deploy identity therefore needs write permission on
    /var/www/hiplingo.com itself, not merely inside the existing
    published-media directory.

    The sticky bit is important: group-write on the parent is required for
    sibling staging, but the sticky bit prevents deploy-hiplingo-media from
    renaming/removing the root-owned app entry.

19. nginx/www-data is intentionally NOT a member of hiplingo-media-deploy.
    Public media is served read-only through:

        /media/ -> /var/www/hiplingo.com/published-media/

    Public directories should be 0755 and public files should be 0644.
    Do not solve nginx read failures by adding www-data to a deployment group
    or by using chmod 777.

20. Private Library waveform binaries may intentionally be mode 0600. That
    private mode must NOT cross the publication boundary. metadata-editor's
    public-package writer normalizes copied public assets to 0644, and the
    production rsync layer independently enforces:

        directories -> 0755
        files       -> 0644

    This was added after the initial production deployment exposed
    waveform-peaks.wfp as mode 0600, causing nginx HTTP 403 responses.

21. The public URL is /media/, not /published-media/. The latter is the
    server-side directory name. Requests to /published-media/... fall through
    to the SPA route and are not the public media contract.

6D. HIPLINGO PUBLIC-MEDIA DEPLOYMENT / SERVING PERMISSIONS
----------------------------------------------------------------------

Why this belongs in the server runbook
--------------------------------------
Hiplingo media is deployed independently from the frontend application.
metadata-editor uses an atomic staging-and-swap workflow, while nginx serves
the resulting tree read-only.

The important distinction is between deployment write permission, needed by
deploy-hiplingo-media, and public read permission, needed by nginx/www-data.

Current production boundary
----------------------------

    /var/www/hiplingo.com
        owner: root
        group: hiplingo-media-deploy
        mode:  3775
        text:  drwxrwsr-t

    /var/www/hiplingo.com/app
        owner: root
        group: hiplingo-app-deploy
        mode:  2775
        text:  drwxrwsr-x

    /var/www/hiplingo.com/published-media
        owner: deploy-hiplingo-media
        group: hiplingo-media-deploy
        normal live mode after atomic sync: 0755

The 3775 parent mode is intentional:

    2xxx = SGID
        new sibling entries inherit hiplingo-media-deploy

    1xxx = sticky bit
        group members cannot remove/rename root-owned siblings such as app

    group write
        permits the media deploy identity to create temporary siblings used
        by the atomic deployment workflow

Do NOT replace 3775 with a broad 0777-style permission. Do NOT add www-data
to hiplingo-media-deploy.

Atomic staging permission probe
-------------------------------

LOCAL CLIENT

SAFE TO PASTE: YES

    ssh hiplingo-prod '
    probe="/var/www/hiplingo.com/published-media.metadata-editor-permission-probe.$$"
    mkdir "$probe" &&

Public-file readability
-----------------------
The private Library and the public package intentionally have different mode
requirements.

Private Library example:

    waveform-peaks.wfp -> 0600 is acceptable/private

Public package / production:

    directories        -> 0755
    files              -> 0644
    waveform-peaks.wfp -> 0644

The publication writer and deployment rsync both normalize this boundary.
This prevents a private source mode from becoming a public nginx 403 after a
future package refresh.

Current production architecture

Monit does NOT invoke a shell helper to send alerts.

Instead:

      |

      |
      v
    /etc/postfix/admin-forwarding.regexp
      |
      v
    ADMIN_FORWARD_TARGET

This avoids extra executable code and avoids granting Monit write access to
Postfix's maildrop directory.

Authoritative file:

    /etc/monit/conf.d/mail-alerts

Ownership target:
    root:root

Mode target:
    600

Logical production form:

    set mailserver 127.0.0.1 port 25
        with timeout 15 seconds

                 Service:     $SERVICE
                 Event:       $EVENT
                 Event time:  $DATE
                 Action:      $ACTION

                 Description:
                 $DESCRIPTION

======================================================================
22. SECURITY PROPERTIES
======================================================================

Mail transport / forwarding
---------------------------
- No Gmail SMTP relay, API, or app-password dependency.
- Operational/admin and business/contact destinations are logically separate.
- Direct-to-MX Postfix delivery is used for outbound mail.
- Public SMTP is IPv4-only and bound only to loopback + 45.32.88.137.
- nftables default-drop remains in force; TCP/25 is explicitly allowed.
- Unknown virtual-domain recipients are rejected.
- No catch-all aliases.
- Unauthenticated external relay is rejected.
- mynetworks trusts loopback only.
- No IMAP, POP3, submission/587, or SMTPS/465 service is exposed.

Authentication / forwarding
---------------------------
- Operational mail is DKIM-signed.
- ops.nathanbrenton.com has narrow SPF authorization and DMARC.
- Public contact forwarding uses PostSRSd.
- srs.nathanbrenton.com SPF authorizes only the production IPv4.
- Signed SRS reverse addresses are accepted; forged SRS addresses fail.
- PostSRSd lookup services are loopback-only.
- Original forwarded message content is preserved so sender DKIM can survive.
- SRS repairs forwarding envelope/SPF transport identity, not original From:
  domain SPF alignment for DMARC.

TLS
---
- SMTP/25 advertises opportunistic STARTTLS.
- Dedicated Let's Encrypt certificate matches web-prod-01.nathanbrenton.com.
- External TLS validation passed using TLS 1.3.
- Certbot deploy hook reloads Postfix after certificate renewal.
- Certbot dry-run with deploy hooks succeeded.
- Postfix's normal reload status line may be labeled by Certbot as hook
  "error output"; this is cosmetic only when renewal and Postfix checks pass.

Web hardening
-------------
- SPA fallback no longer returns HTTP 200 for hidden-file probes.
- nginx explicitly returns 404 for /.git/*, /.env, and other hidden paths.
- Audit found no physical .git/config or .env files in either deployed tree.
- SMTP-host ACME challenge serving is isolated in a dedicated nginx vhost.


Hiplingo public-media boundary
------------------------------
- /var/www/hiplingo.com is root:hiplingo-media-deploy mode 3775 so the
  dedicated media deploy identity can create atomic sibling staging paths.
- The sticky bit protects root-owned sibling entries such as app from
  rename/removal by the media deployment group.
- /var/www/hiplingo.com/app remains a separate hiplingo-app-deploy boundary.
- published-media is owned by deploy-hiplingo-media after atomic publication.
- nginx/www-data is not granted deployment-group membership.
- Public directories are normalized to 0755 and files to 0644.
- Private Library waveform mode 0600 is retained privately and is normalized
  to 0644 only when crossing into the public package.
- /media/ is the public URL prefix; /published-media/ is an internal path name.

Monitoring
----------
- Monit TCP/2812 is not exposed.
- Monit CLI uses a root-only Unix socket.
- Monit sends alerts with native SMTP to 127.0.0.1:25.
- No production server-monitor-alert EXEC helper is required.
- No Postfix maildrop sandbox exception is required for Monit alerts.
- Production service checks are alert-only.
- PostSRSd is monitored alongside Postfix and OpenDKIM.
- Daily reporting and immediate Monit alerts remain separate mechanisms.

route outbound mail, software on that same VPS cannot send an alert describing
that outage.

Current production mitigation:
    independent Better Stack HTTPS/content monitoring plus daily/weekly
    report heartbeats. This external layer is part of the rebuild baseline.

Grafana 13 stores dashboards using Unified Storage.

Current SQLite database:

    /var/lib/grafana/grafana.db

Do NOT assume the legacy "dashboard" table contains current dashboards.

Validated current behavior:

    legacy table:
        dashboard rows = 0

    current Unified Storage table:
        resource

    dashboard resource selector:
        group    = dashboard.grafana.app
        resource = dashboards
        namespace = default

The v1 dashboard was stored as one dashboard resource.

Read-only inspection pattern:

    sudo python3 <<'PY'
    import json
    import sqlite3

    con = sqlite3.connect(
        "file:/var/lib/grafana/grafana.db?mode=ro",
        uri=True
    )

    rows = con.execute("""
        SELECT name, namespace, resource_version, value
        FROM resource
        WHERE "group"='dashboard.grafana.app'
          AND resource='dashboards'
        ORDER BY resource_version DESC
    """).fetchall()

    print("dashboard resources:", len(rows))

    for name, namespace, version, raw in rows:
        if isinstance(raw, bytes):
            raw = raw.decode("utf-8")

        obj = json.loads(raw)

        print(
            "name=", name,
            "namespace=", namespace,
            "version=", version,
            "title=", obj.get("spec", {}).get("title"),
            "elements=", len(obj.get("spec", {}).get("elements", {})),
        )

    con.close()
    PY

Current expected title:

    web-prod-01 - Operations

Current expected element/panel count:

    34

Rebuild recommendation
----------------------
The runbook is sufficient to reconstruct the dashboard manually, but before a
future destructive rebuild also preserve a dashboard export/backup separately.

Treat Grafana's SQLite file as application state, not as the only source of
truth. A future documentation milestone should add a source-controlled
dashboard export once the dashboard stabilizes further.

37. OBSERVABILITY SECURITY / OPERATING POLICY
======================================================================

1. Prometheus, Alertmanager, node_exporter, Blackbox Exporter, Loki and Alloy
   remain loopback only.

2. Grafana also binds only to loopback when it is started. Grafana is
   intentionally disabled at boot and is an on-demand investigation UI on
   this resource-limited host.

3. Do not add public nftables rules for TCP:
       3000   Grafana
       9090   Prometheus
       9093   Alertmanager
       9100   node_exporter
       9115   Blackbox Exporter
       3100   Loki HTTP
       9096   Loki gRPC
       12345  Alloy local HTTP/UI/metrics

   Alertmanager HA/gossip TCP/UDP 9094 remains disabled entirely on this
   single-node deployment.

4. Grafana administrative access remains through SSH local port forwarding.

5. node_exporter, Prometheus, Loki and Alloy run as dedicated unprivileged
   service identities. Loki writes only beneath /var/lib/loki. Alloy keeps its
   state beneath /var/lib/alloy.

6. Blackbox Exporter probes the two public HTTPS sites at a low rate
   (60-second Prometheus scrape interval). This is normal observability traffic,
   not load testing.

7. Blackbox Exporter journal logs are deliberately excluded from Alloy's
   journald ingestion because they dominated local journal line volume while
   Prometheus already retains the useful probe telemetry.

8. nginx access/error logs are ingested separately through Alloy's file source.
   Blackbox-generated HTTP requests therefore still appear in nginx access
   logs. Filtering those self-probe access lines is an optional future
   optimization, not a correctness requirement.

9. External server testing remains deliberately low-noise:
       - prefer local/on-box validation first;
       - use narrowly targeted tests only against owned hosts;
       - avoid broad scanning, fuzzing, brute-force behavior or high-rate
         probes.

10. Monit remains independent of Prometheus/Alertmanager/Loki/Alloy and should
    not be removed merely because metrics and logs exist. Monit is alert-only;
    systemd remains authoritative for lifecycle/restart behavior.

11. Grafana is intentionally NOT watched by Monit as an always-on service.
    Its inactive state is normal production state.

12. Do not configure automatic production-service remediation solely from
    Prometheus/Grafana/Loki data without a deliberate operational policy.

13. Historical metrics/logs are useful only while the host itself remains
    reachable. Same-host Prometheus/Loki cannot report complete VPS loss while
    the VPS is offline.

14. Treat Grafana exported-log duplication separately from ingestion
    duplication. A controlled direct Loki marker test proved one generated
    nginx event is stored exactly once. Do not add Alloy/Loki deduplication
    merely because a Grafana text export renders identical rows twice.

44. MONIT INDEPENDENT OBSERVABILITY WATCHDOG
======================================================================

Why it exists
-------------
Prometheus cannot reliably report its own complete process loss because no rule
engine remains to evaluate alerts. Alertmanager cannot send an
Alertmanager-based notification when Alertmanager itself is unavailable.

Monit therefore remains an independent local watchdog with its own direct
Postfix alert path.

File:

    /etc/monit/conf.d/systemd-services

Checks added:

    check program node-exporter-systemd
        with path "/usr/bin/systemctl is-active node_exporter.service"
        if status != 0 for 2 cycles then alert

    check program prometheus-systemd
        with path "/usr/bin/systemctl is-active prometheus.service"
        if status != 0 for 2 cycles then alert

    check program alertmanager-systemd
        with path "/usr/bin/systemctl is-active prometheus-alertmanager.service"
        if status != 0 for 2 cycles then alert

    check program blackbox-exporter-systemd
        with path "/usr/bin/systemctl is-active prometheus-blackbox-exporter.service"
        if status != 0 for 2 cycles then alert

    # Grafana is deliberately NOT present here. It is an on-demand
    # investigation UI and may normally be inactive/disabled.

At a 120-second Monit interval, two failed cycles are approximately four
minutes of sustained failure.

systemd remains authoritative for lifecycle/restarts. These checks ALERT ONLY.

Weekly memory-pressure implementation — 2026-09-08
---------------------------------------------------

The weekly digest reports pressure separately from ordinary RAM utilization.

Required node_exporter counters:

    node_pressure_memory_waiting_seconds_total
    node_pressure_memory_stalled_seconds_total

Seven-day PSI "some" p95:

    quantile_over_time(
      0.95,
      (
        100 *
        rate(node_pressure_memory_waiting_seconds_total[5m])
      )[7d:5m]
    )

Seven-day PSI "full" p95:

    quantile_over_time(
      0.95,
      (
        100 *
        rate(node_pressure_memory_stalled_seconds_total[5m])
      )[7d:5m]
    )

The multiplication by 100 converts the stall-time ratio into percentage of
wall time. Report with four decimal places so a healthy low-pressure host does
not collapse useful resolution into 0.00%.

Kernel OOM history is read directly from the kernel journal for the trailing
seven days. Count standard records matching:

    Out of memory: Killed process <PID>

rather than every OOM-related log line, to reduce double-counting of a single
kill event.

Current report shape:

    MEMORY PRESSURE — 7 DAYS
    ------------------------
    Kernel OOM kills:     0
    PSI some p95:         0.0004%
    PSI full p95:         0.0003%
    Note: PSI is percentage of wall time delayed by memory pressure.

The values above are an example validated on 2026-09-08 and are NOT fixed
thresholds. The destination server's real measurements must populate them.

If Prometheus is unavailable, PSI fields follow the report's existing graceful
degradation policy and render n/a. Kernel OOM history remains a direct local
check.

55. RESOURCE-CONSTRAINED INSTALLATION / COMMISSIONING GUIDANCE
======================================================================

This section is mandatory guidance for rebuilding this stack on a small VPS.

Baseline principle
------------------
Do not install multiple observability components and only measure afterward.

Before each additional service:
    - measure available RAM;
    - inspect swap occupancy AND swap-in/swap-out activity;
    - inspect Linux PSI;
    - inspect root filesystem headroom;
    - inspect journal/log volume;
    - check current Prometheus alerts;
    - establish a reversible configuration/backup point.

Then:
    - install/configure ONE component;
    - validate it;
    - let it settle;
    - re-measure;
    - continue only if the host remains healthy.

The /tmp tmpfs commissioning incident
-------------------------------------
This host's /tmp is tmpfs-backed and was approximately:

    481 MiB

A package-inspection extraction under /tmp grew to approximately:

    447 MiB

Consequences observed:
    - /tmp reached 100%;
    - available RAM fell sharply;
    - swap occupancy grew from roughly 85 MiB to roughly 335 MiB.

No observability service had been installed by that failed extraction attempt.

After deleting the temporary inspection tree:
    - /tmp recovered immediately;
    - available RAM recovered;
    - swap occupancy fell substantially;
    - vmstat returned to no sustained swap traffic.

Rule:
    large package extraction/inspection on a small host must use a disk-backed
    path such as /var/tmp, not /tmp, unless /tmp has first been verified to be
    disk-backed and adequately sized.

Before using temporary space:
    findmnt /tmp
    df -h /tmp /var/tmp /
    free -h

Preferred package-inspection workspace:

    /var/tmp/alloy-loki-package-inspection

Swap interpretation
-------------------
Do NOT use swap occupancy alone as the incident criterion.

A Linux host may leave cold pages in swap even after memory pressure ends.

More meaningful indicators:
    vmstat si
    vmstat so
    /proc/pressure/memory
    available memory
    sustained CPU/I/O wait
    service latency/failures
    Prometheus resource-pressure alerts

Do NOT run swapoff merely to make the swap-used number look smaller on this
memory-constrained production host. swapoff can force all swapped pages back
into RAM and create the pressure the operator is trying to avoid.

Use:

    free -h
    vmstat 1 10
    cat /proc/pressure/memory

Healthy steady-state guidance:
    - occupied swap can be non-zero;
    - sustained si/so should normally settle near zero;
    - PSI avg10 should return near zero after transient work;
    - no OOM events;
    - no active/pending resource-pressure alerts.

Package post-install behavior matters
-------------------------------------
Inspect package scripts before configuration when a package may auto-start a
large daemon.

Alloy 1.18.1-1 clean-install behavior observed:
    - creates alloy identity/groups/data directories;
    - grants required adm/systemd-journal membership;
    - clean install does NOT automatically start Alloy;
    - package upgrade can restart depending on RESTART_ON_UPGRADE.

Loki 3.7.6 clean-install behavior observed:
    - creates the loki identity;
    - daemon-reload/unmask/preset;
    - enables and restarts Loki during package configuration.

Therefore, on a small host, Loki should be staged with the equivalent of:
    1. download package;
    2. dpkg --unpack;
    3. replace package-default configuration;
    4. create resource-control drop-in;
    5. validate config;
    6. only then dpkg --configure.

Do not let Loki's package-default configuration become the production
configuration merely because package installation can start the service.

Package-default Loki settings specifically rejected for this host included:
    - /tmp/loki storage;
    - debug logging;
    - large embedded results cache;
    - metric aggregation / multi-variant features;
    - pattern ingester;
    - unnecessary ruler behavior.

Resource controls
-----------------
MemoryHigh is the soft-pressure boundary.
MemoryMax is the hard cgroup ceiling.
GOMEMLIMIT guides the Go runtime before cgroup hard pressure.
TasksMax limits runaway process/thread growth.

These controls do NOT replace capacity planning. They are guardrails.

Measured commissioning behavior
--------------------------------
With Grafana OFF and Loki + Alloy ON:
    - available RAM was roughly 500+ MiB in several validation samples;
    - sustained vmstat si/so settled to zero;
    - PSI avg10 settled to zero;
    - no Prometheus ALERTS were active.

With Grafana temporarily ON in addition to Loki + Alloy:
    - Grafana cgroup memory was roughly 360-390 MiB in validation samples;
    - available RAM fell into roughly the 300-MiB range;
    - measurable memory PSI appeared;
    - no alert fired during the short controlled session;
    - available RAM recovered after Grafana stopped.

An earlier all-on commissioning test produced substantially worse pressure,
including active paging and pending memory/swap-pressure alerts.

Conclusion:
    Loki + Alloy are appropriate always-on services at current scale.
    Grafana is appropriate as an on-demand investigation service.
    Continuous Grafana operation is not justified on the current 1-GiB plan.

When to prefer a RAM upgrade
----------------------------
Further tuning is not always the right engineering choice.

Prefer upgrading to at least a 2-GiB RAM plan when any of the following becomes
normal rather than exceptional:
    - Grafana needs to remain continuously available;
    - Loki ingestion/query load grows materially;
    - application workloads increase;
    - active swap I/O persists during normal steady state;
    - PSI remains elevated;
    - cgroup MemoryHigh is routinely crossed;
    - OOM/restarts occur;
    - resource-alert thresholds require repeated relaxation merely to keep the
      current workload alive.

The purpose of this architecture is to operate safely within current
constraints, not to disguise a host that has outgrown its capacity.

59. INDEPENDENT EXTERNAL UPTIME + HEARTBEAT MONITORING — 2026-08-25

Purpose
-------
The local observability stack cannot independently report a complete VPS,
network, provider, or public-path outage when the monitored host itself is
unreachable. Better Stack Uptime provides a deliberately separate external
monitoring layer for that failure class.

This layer supplements rather than replaces:
    - Monit local watchdogs;
    - Prometheus metrics and production alert rules;
    - Alertmanager notification routing;
    - Blackbox Exporter local HTTPS probes;
    - Alloy + Loki local log aggregation;
    - Grafana on-demand inspection.

No Better Stack agent is required on web-prod-01 for the commissioned design.
No Prometheus, Grafana, Loki, Alloy, node_exporter, Alertmanager, or Blackbox
listener is exposed publicly for Better Stack.

Public firewall policy therefore remains unchanged.

-----------------------
Commissioned canonical public-site monitors:

    https://hiplingo.com/
    https://nathanbrenton.com/

Monitor purpose:
    detect public HTTPS/TLS/content failure independently of web-prod-01.

Current low-noise monitor posture after post-commissioning tuning:
    - HTTP method: GET
    - check frequency: 3 minutes
    - confirmation period: 3 minutes
    - recovery period: 3 minutes
    - request timeout: 10 seconds
    - follow redirects: enabled
    - SSL/TLS verification: enabled
    - IP version: both IPv4 and IPv6
    - geographically distributed checks retained
    - no recurring maintenance window
    - primary responder email enabled
    - phone/SMS escalation not required for current scale
    - no deliberate production outage is required for testing

        response must contain: Hiplingo

    nathanbrenton.com
        response must contain: Nathan Brenton

This catches a healthy HTTP transport that accidentally serves an empty,

Heartbeat semantics
-------------------
A heartbeat means:

    the scheduled report reached its successful local mail-submission boundary

It does NOT mean:

    all health checks were green

Therefore a DAILY WARNING report may still emit a successful heartbeat. That
is intentional. The report process worked even though the report itself found
a warning condition.

The daily and weekly scripts both use this control flow:

    --preview
        -> render only
        -> no email
        -> no heartbeat

    normal run
        -> render report
        -> submit mail through local sendmail
        -> verify sendmail exit status == 0
        -> log report-submitted marker
        -> attempt Better Stack heartbeat

A sendmail failure remains fatal to the report service and prevents the
success heartbeat.

A temporary Better Stack/network failure is intentionally NON-FATAL to the
report service. The report has already succeeded at its local mail-submission
boundary, so a third-party heartbeat failure must not rewrite that local job
result. Better Stack detects the absence of future heartbeat reception on its
own schedule.

Heartbeat implementation characteristics
----------------------------------------
Both scripts:
    - read the secret URL only after successful sendmail submission;
    - strip CR/LF from the root-only URL file;
    - require an https:// URL;
    - pass the URL to curl through stdin/config input rather than placing the
      secret directly in the curl command-line arguments;
    - use a 5-second connect timeout;
    - use a 10-second total timeout;
    - discard heartbeat response bodies;
    - log heartbeat=sent on success;
    - log heartbeat=failed or heartbeat=skipped on local heartbeat problems;
    - do not convert heartbeat transport failure into report-service failure.

Manual service test vs timer LAST field
---------------------------------------
A manual command such as:

    sudo systemctl start server-weekly-report.service

directly invokes the service. It does not count as the timer itself firing.
Therefore this is expected after a manual commissioning run when the timer has
not yet fired naturally:

    LAST -

The first natural Monday timer execution populates the timer's LAST field.

Secret installation / recovery
------------------------------
When rebuilding the server or rotating a Better Stack heartbeat URL, obtain the
correct UNIQUE URL from that specific Better Stack heartbeat resource.

Never reuse the daily URL for weekly or the weekly URL for daily.

Daily secret example:

    read -rsp "Paste Better Stack DAILY heartbeat URL, then press Enter: " HEARTBEAT_URL
    echo
    printf '%s\n' "$HEARTBEAT_URL" | \
      sudo tee /etc/server-monitor/daily-health-heartbeat-url >/dev/null
    unset HEARTBEAT_URL
    sudo chown root:root /etc/server-monitor/daily-health-heartbeat-url
    sudo chmod 0600 /etc/server-monitor/daily-health-heartbeat-url

Weekly secret example:

    read -rsp "Paste Better Stack WEEKLY heartbeat URL, then press Enter: " HEARTBEAT_URL
    echo
    printf '%s\n' "$HEARTBEAT_URL" | \
      sudo tee /etc/server-monitor/weekly-operations-heartbeat-url >/dev/null
    unset HEARTBEAT_URL
    sudo chown root:root /etc/server-monitor/weekly-operations-heartbeat-url
    sudo chmod 0600 /etc/server-monitor/weekly-operations-heartbeat-url

Validate metadata without printing either URL:

    sudo stat -c 'owner=%U:%G mode=%a bytes=%s path=%n' \
      /etc/server-monitor/daily-health-heartbeat-url \
      /etc/server-monitor/weekly-operations-heartbeat-url

Validate format without revealing the secret:

    sudo python3 - <<'PY'
    from pathlib import Path

    for name in (
        "daily-health-heartbeat-url",
        "weekly-operations-heartbeat-url",
    ):
        p = Path("/etc/server-monitor") / name
        value = p.read_text().strip()
        if not value:
            raise SystemExit(f"STOP: {name} is empty")
        if not value.startswith("https://"):
            raise SystemExit(f"STOP: {name} is not HTTPS")
        print(f"PASS: {name}: non-empty HTTPS URL; length={len(value)}")
    PY

Do not cat either secret file during routine validation.

Controlled validation after rebuild or URL rotation
---------------------------------------------------
First validate preview behavior:

    sudo /usr/local/sbin/server-health-report --preview >/dev/null && \
      echo "daily_preview=PASS"

    sudo /usr/local/sbin/server-weekly-report --preview >/dev/null && \
      echo "weekly_preview=PASS"

Preview MUST NOT send email or heartbeat.

Then test the desired real job once through systemd. This deliberately sends
one report email and one heartbeat:

    sudo systemctl start server-health-report.service

or:

    sudo systemctl start server-weekly-report.service

Inspect only non-secret markers:

    sudo journalctl -u server-health-report.service --since '-5 minutes' \
      --no-pager | \
      grep -E 'health_report_submitted=|status=|heartbeat='

    sudo journalctl -u server-weekly-report.service --since '-5 minutes' \
      --no-pager | \
      grep -E 'weekly_report_submitted=|status=|heartbeat='

Expected successful heartbeat marker:

    heartbeat=sent

Then confirm:
    - report service Result=success;
    - ExecMainStatus=0;
    - Postfix queue drains;
    - mail log reports status=sent;
    - correct Better Stack heartbeat shows a fresh receipt;
    - the corresponding systemd timer remains active + enabled.

Heartbeat URL rotation
----------------------
Treat rotation as a credential change:
    1. create/obtain the replacement URL for the SAME heartbeat monitor;
    2. replace only the corresponding root-only local secret file;
    3. retain root:root 0600 permissions;
    4. do not place the replacement URL in Git, docs, shell scripts, tickets,
       screenshots, or chat transcripts;
    5. run preview first;
    6. run one controlled real service test;
    7. confirm heartbeat receipt in Better Stack;
    8. confirm mail delivery and timer state.

If a heartbeat monitor itself is replaced rather than merely rotated, verify
its cadence and grace period before changing the server secret file.

Failure interpretation
----------------------
External HTTPS incident:
    public site could be unavailable even if local services appear healthy.
    Validate from the external provider first, then inspect nginx, network,
    DNS/TLS, host state, and provider state as appropriate.

Missed heartbeat with site still UP:
    inspect the corresponding report timer/service, report logs, secret-file
    metadata, outbound HTTPS reachability, and Better Stack monitor state.

heartbeat=failed with report Result=success:
    the local report completed successfully but the heartbeat transport did
    not. Do not rewrite the report result. Investigate outbound connectivity
    and Better Stack separately.

Report service failed and no heartbeat arrived:
    expected behavior. Diagnose the local report failure first.

Complete VPS/network loss:
    the independent external HTTPS monitors can create an incident even though
    web-prod-01 itself cannot send local alerts or heartbeats.

Security / architecture invariant
---------------------------------
Better Stack remains an OUTSIDE observer.

Do not solve external monitoring by exposing:
    127.0.0.1:9090 Prometheus
    127.0.0.1:9093 Alertmanager
    127.0.0.1:9100 node_exporter
    127.0.0.1:9115 Blackbox Exporter
    127.0.0.1:12345 Alloy
    127.0.0.1:3100 Loki
    127.0.0.1:3000 Grafana

The commissioned design needs only:
    - existing public HTTPS for the websites;
    - outbound HTTPS from the server for heartbeats;
    - the existing mail path for local reports/alerts.

No inbound observability firewall change is required.

    sustained-cycle durations
    swap size
    disk thresholds/growth assumptions
    Prometheus retention size/time
    Loki retention/resource limits
    Alloy resource limits
    Grafana boot policy
    cgroup MemoryHigh/MemoryMax/GOMEMLIMIT
    public IP
    FQDN/domain targets
    operations email aliases
    deployment identities/paths

Weekly PSI/OOM first-build gate
-------------------------------
Before installing/commissioning server-weekly-report:

    1. prove node_exporter is serving both:
           node_pressure_memory_waiting_seconds_total
           node_pressure_memory_stalled_seconds_total

    2. prove Prometheus has both series;

    3. run the two 7-day p95 PromQL expressions (shorter history is acceptable
       during first commissioning; the result will mature as retention fills);

    4. verify kernel journal access for OOM history;

    5. run server-weekly-report --preview and require the MEMORY PRESSURE
       section to render;

    6. only then perform the controlled systemd/mail test and enable/retain the
       weekly timer.

No additional daemon, public listener, or new alert rule is required for this
metric.
