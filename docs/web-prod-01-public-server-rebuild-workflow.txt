WEB-PROD-01 PUBLIC SERVER REBUILD WORKFLOW
Debian 13 (trixie) + nginx + Postfix/OpenDKIM/PostSRSd
Updated: 2026-08-19 (America/Los_Angeles)
Domains: nathanbrenton.com + hiplingo.com

Purpose
=======
This is a command-by-command rebuild procedure for recreating the validated
public-server foundation from a fresh Debian 13 host.

It includes the public contact-mail forwarding architecture commissioned in
August 2026 and the nginx hidden-path hardening added after scanner probes for
/.git/config and /.env.

The August 19, 2026 PT10 mail update adds a canonical operations alias
(admin@hiplingo.com), a separate admin forwarding map, expanded business role
addresses, and the "Hiplingo Server Monitor" display identity.

It intentionally avoids abandoned/backtracked approaches. In particular:

  - Use nftables directly.
  - Do NOT use UFW alongside nftables.
  - Use journald as Fail2ban's SSH log source; do not add rsyslog just for Fail2ban.
  - Keep nathanbrenton.com, Hiplingo frontend, and Hiplingo published media as
    separate deployment/write boundaries.
  - Hiplingo media deployment is atomic and uses sibling staging paths under
    /var/www/hiplingo.com; configure that parent as root:hiplingo-media-deploy
    mode 3775 (SGID + group-write + sticky bit), not root:root 0755.
  - Keep nginx/www-data read-only; public media directories are 0755 and files
    are 0644. Do not add www-data to a deployment group.
  - Do not publish the private metadata-editor media-library.
  - Do not enable automatic reboots after unattended upgrades.
  - Do not store SSH backup files under /etc/ssh/sshd_config.d/ because this
    Debian image includes *.conf* from that directory.
  - Do not expose SMTP/25 until exact-recipient validation, anti-relay tests,
    SRS, DNS, and SMTP TLS have all been staged and validated locally.
  - Do not run a catch-all public mail domain.
  - Do not expose IMAP, POP3, TCP/587, or TCP/465.
  - Keep operational/status recipient configuration separate from public
    business/contact forwarding even if both currently use the same inbox.
  - Treat SPA fallback HTTP 200 responses for hidden-looking paths as a
    security smell; explicitly return 404 for hidden paths.

This runbook ends at the CURRENT VALIDATED SERVER-READY STATE.
The following application/content operations remain intentionally separate:

  - real nathanbrenton.com site deployment
  - real hiplingo.com frontend deployment
  - metadata-editor published-media export/sync to production

MAIL-TECHNOLOGY NOTES
=====================

SRS / SPF
---------
Forwarding ordinarily causes SPF trouble because the final receiver sees the
forwarding VPS, not the original sender's SMTP IP. PostSRSd rewrites the SMTP
envelope sender to a signed address under srs.nathanbrenton.com. That domain's
SPF authorizes this VPS, and signed SRS addresses can later be reversed for
bounces.

SRS changes the envelope/Return-Path identity; it should not rewrite the
visible From: header or message body.

DKIM / DMARC during forwarding
------------------------------
SRS does not make SPF align with the original visible From: domain for DMARC.
Therefore preserving the original sender's DKIM signature is important.
Aligned DKIM can continue to satisfy DMARC after forwarding.

Virtual aliases
---------------
nathanbrenton.com and hiplingo.com are Postfix virtual alias domains, not local
mailbox domains. Only explicitly mapped recipients are accepted. The SRS
subdomain is also a virtual alias domain, with dynamic reverse lookup through
PostSRSd.

Monitoring mail transport
-------------------------
Production Monit uses its built-in SMTP client:

    set mailserver 127.0.0.1 port 25
        with timeout 15 seconds

Do not recreate the older experimental server-monitor-alert EXEC bridge or a
Postfix maildrop ReadWritePaths exception.

The operations/admin producers share one stable internal recipient:

    /etc/server-monitor/config
        ADMIN_EMAIL=admin@hiplingo.com

    /etc/monit/conf.d/mail-alerts
        set alert admin@hiplingo.com

The real operations inbox is stored only in the admin Postfix map.


Recipient separation
--------------------
Two independent real forwarding destinations intentionally exist:

  ADMIN_FORWARD_TARGET
      right-hand destination in /etc/postfix/admin-forwarding.regexp
      operations / health / alert mail

  CONTACT_FORWARD_TARGET
      right-hand destination in /etc/postfix/contact-forwarding.regexp
      public business/contact forwarding

They may currently contain the same literal inbox. Do not deduplicate them
into one setting; changing either destination later must not affect the other.

ADMIN_EMAIL is deliberately not a real destination setting. It remains:

    ADMIN_EMAIL=admin@hiplingo.com

9. PUBLIC SERVER — CONFIGURE NFTABLES BOOTSTRAP FIREWALL
===========================================================

Run on: PUBLIC SERVER as n8
Output: SAFE TO PASTE.

Keep a known-good SSH session open while applying firewall changes.

At this EARLY rebuild stage, intentionally permit only 22/80/443.
Do NOT open TCP/25 yet. The mail commissioning sections later add TCP/25 only
after Postfix recipient policy, SRS, TLS, DNS, and anti-relay validation pass.

    sudo tee /etc/nftables.conf >/dev/null <<'EOF_NFT'
#!/usr/sbin/nft -f

flush ruleset

table inet filter {
    chain input {
        type filter hook input priority filter; policy drop;

        ct state invalid drop
        ct state established,related accept

        iifname "lo" accept

        ip protocol icmp accept
        meta l4proto ipv6-icmp accept

        tcp dport { 22, 80, 443 } ct state new accept
    }

    chain forward {
        type filter hook forward priority filter; policy drop;
    }

    chain output {
        type filter hook output priority filter; policy accept;
    }
}
EOF_NFT

Syntax-check without applying:

    sudo nft -c -f /etc/nftables.conf

Enable and apply:

    sudo systemctl enable nftables
    sudo systemctl restart nftables

Validate:

    systemctl is-active nftables
    systemctl is-enabled nftables
    sudo nft list ruleset

Expected base table:

    table inet filter

Expected bootstrap inbound policy:

    established/related accepted
    loopback accepted
    ICMP/ICMPv6 accepted
    TCP 22/80/443 accepted
    TCP/25 NOT YET accepted
    everything else inbound dropped

Final production state after mail commissioning:
    TCP 22/25/80/443 accepted.

13. PUBLIC SERVER — CREATE DEPLOYMENT FILESYSTEM BOUNDARIES
==========================================================

Run on: PUBLIC SERVER as n8
Output: SAFE TO PASTE.

Nathan's frontend and Hiplingo's frontend use ordinary SGID deployment trees.
Hiplingo public media is different because metadata-editor performs an ATOMIC
sibling-stage-and-swap deployment. The media deploy identity must therefore
create paths beside published-media, not merely write inside it.

Create Nathan's independent release tree:

    sudo install -d -m 2775 -o root -g nathan-deploy \
      /var/www/nathanbrenton.com

    sudo install -d -m 2775 -o root -g nathan-deploy \
      /var/www/nathanbrenton.com/releases

Create the Hiplingo parent with the media deployment group:

    sudo install -d -m 3775 -o root -g hiplingo-media-deploy \
      /var/www/hiplingo.com

Mode 3775 means:

    2xxx  SGID
          new sibling entries inherit hiplingo-media-deploy

    1xxx  sticky bit
          deploy-hiplingo-media may manage entries it owns, but cannot
          rename/remove root-owned sibling entries such as "app"

    0775  the media deployment group may create atomic sibling staging paths

This is intentionally narrower than chmod 777. Do not remove the sticky bit:
without it, group-write on the parent would unnecessarily weaken the frontend
boundary.

Create Hiplingo's independent frontend tree:

    sudo install -d -m 2775 -o root -g hiplingo-app-deploy \
      /var/www/hiplingo.com/app

    sudo install -d -m 2775 -o root -g hiplingo-app-deploy \
      /var/www/hiplingo.com/app/releases

Create the INITIAL empty media tree so deploy-hiplingo-media owns the object
that the atomic deploy later needs to rename:

    sudo install -d -m 2775 \
      -o deploy-hiplingo-media \
      -g hiplingo-media-deploy \
      /var/www/hiplingo.com/published-media

IMPORTANT:
    The first successful atomic rsync deployment replaces the initial empty
    directory with its staged tree. Current deployment tooling explicitly
    normalizes public directories to 0755 and files to 0644, so the normal
    post-deployment live root is expected to become:

        deploy-hiplingo-media:hiplingo-media-deploy 0755
        /var/www/hiplingo.com/published-media

    That is correct. The deploy identity owns the live tree and obtains its
    rename/create authority from the 3775 parent.

Why published-media must initially be owned by deploy-hiplingo-media:
    On a sticky parent, a group member cannot rename a root-owned child.
    Creating the initial published-media directory as root would therefore
    block the first atomic swap even though the media group can write to the
    parent.

Public/private mode boundary:
    private metadata-editor Library files may intentionally be 0600;
    sanitized published-media files must be web-readable 0644.

    Current metadata-editor defense in depth:
        public package writer -> copied public assets chmod 0644
        deployment rsync      -> directories 0755, files 0644

Do NOT place metadata-editor's private media-library here.
Only sanitized published-media output belongs in published-media/.

Validate:

    stat -c '%A %a %U:%G %n' \
      /var/www/nathanbrenton.com \
      /var/www/nathanbrenton.com/releases \
      /var/www/hiplingo.com \
      /var/www/hiplingo.com/app \
      /var/www/hiplingo.com/app/releases \
      /var/www/hiplingo.com/published-media

Before the first real media deployment, expected Hiplingo entries include:

    /var/www/hiplingo.com
        root:hiplingo-media-deploy 3775

    /var/www/hiplingo.com/app
        root:hiplingo-app-deploy 2775

    /var/www/hiplingo.com/published-media
        deploy-hiplingo-media:hiplingo-media-deploy 2775

19A. PUBLIC SERVER — HARDEN SPA HIDDEN-PATH REQUESTS
====================================================

Run on: PUBLIC SERVER as n8
Output: SAFE TO PASTE.

Why this exists
---------------
During production commissioning, a scanner requested /.git/config and nginx
returned HTTP 200. A careful audit proved there was NO repository disclosure:
the response hash was identical to /index.html, and no .git/config or .env
files existed in either deployed web tree.

The cause was the SPA fallback:

    try_files $uri $uri/ /index.html;

Unknown hidden-looking paths were being converted into successful app-shell
responses.

After Certbot has created the final HTTPS server blocks, add a hidden-path
guard to the APPLICATION server block for each site:

    location ~ /\. {
        return 404;
    }

Do NOT add a generic /.well-known exception here merely for the later SMTP
certificate. The SMTP certificate gets its own dedicated ACME hostname/vhost.

Guarded insertion using the unique application root line:

    for SPEC in \
      '/etc/nginx/sites-enabled/nathanbrenton.com|    root /var/www/nathanbrenton.com/current;' \
      '/etc/nginx/sites-enabled/hiplingo.com|    root /var/www/hiplingo.com/app/current;'
    do
      FILE="${SPEC%%|*}"
      ROOT_LINE="${SPEC#*|}"

      sudo python3 - "$FILE" "$ROOT_LINE" <<'PY'
from pathlib import Path
import sys

path = Path(sys.argv[1])
root_line = sys.argv[2]
text = path.read_text()

needle = root_line + "\n"

if text.count(needle) != 1:
    raise SystemExit(
        f"STOP: expected exactly one application root in {path}"
    )

if "location ~ /\\. {" in text:
    raise SystemExit(
        f"STOP: hidden-path rule already present in {path}"
    )

snippet = r'''
    # Block hidden files/directories before SPA fallback can serve index.html.
    # Examples: /.git/config, /.env, /.ssh/id_rsa
    location ~ /\. {
        return 404;
    }

'''

path.write_text(text.replace(needle, needle + snippet, 1))
PY
    done

Validate BEFORE reload:

    sudo nginx -t

Then:

    sudo systemctl reload nginx

External validation:

    for host in nathanbrenton.com hiplingo.com; do
        printf '%s root=' "$host"
        curl -sS -o /dev/null -w '%{http_code}\n' "https://$host/"

        for path in \
          /.git/config \
          /.env \
          /.env.production \
          /.ssh/id_rsa
        do
            printf '%s %-20s ' "$host" "$path"
            curl -sS -o /dev/null -w '%{http_code}\n' \
              "https://$host$path"
        done
    done

Expected:
    site roots -> 200
    hidden probes -> 404

Defense in depth:
    Deployment tooling should still exclude .git, .env, private keys, and
    secret files. nginx 404 handling is an additional boundary, not permission
    to deploy sensitive files.
